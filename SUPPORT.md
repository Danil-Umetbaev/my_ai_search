# Агент диагностики

Войдите в систему и нажмите «Техподдержка». Диагност последовательно собирает
описание неисправности, окружение, влияние и выполненные проверки. После ответа
«да» создаётся заявка в PostgreSQL. До подтверждения можно исправить описание.
Агент адаптирует сценарий по ответам: распознаёт сведения об окружении,
влиянии и выполненных проверках в одном сообщении и пропускает заполненные пункты.
Для оплаты, печати чеков, сети и входа задаёт разные диагностические вопросы.
Ответы сохраняются в заявке. Неинформативные «да/нет» на вопросы об окружении
и влиянии требуют уточнения; «не знаю» позволяет продолжить с неизвестными данными.
Перед отправкой показывает сводку; поля можно исправить командами
«проблема: …», «окружение: …», «влияние: …», «проверки: …».
«Отмена» завершает обращение без заявки. После изменения проблемы заново выбирается
диагностическая ветка. Старые сохранённые диалоги совместимы.
После готовности моделей диалог использует Qwen: модель получает историю,
факты, гипотезы и результаты поиска по базе знаний. Выбирает один следующий
вопрос, проверку по документации, подготовку заявки или подтверждение решения.
Ответ проверяется по схеме; цитаты сверяются с найденными фрагментами дословно.
В ответ выводятся цитата и источник. Неподтверждённые цитаты и повторные вопросы
переключают диалог на резервный сценарий. Гипотезы сохраняются отдельно от фактов.
Подтверждение решения: «проблема решена». Создание заявки требует отдельного «да».
Агент не выполняет команды на устройствах.

Сайт, авторизация и заявки запускаются независимо от моделей. Модели загружаются
в фоновом потоке; `/api/v1/health` возвращает `models: loading/ready/failed`.
Пока модели недоступны, диагностика использует правила, а поиск возвращает 503.
База знаний должна быть наполнена по инструкции README: в пустой базе источников
для проверок нет. Применимость цитат и качество вопросов требуют проверки на
реальной модели и документах: строгий JSON сам по себе не гарантирует верный диагноз.
История и состояние сохраняются на сервере; браузер хранит идентификатор диалога.
«Завершить диалог» позволяет начать новое обращение при следующем открытии.

## Запуск

Используйте настройки и Docker Compose из README.md. Перед запуском новой версии
примените миграции: из backend выполните `alembic upgrade head` с настроенным .env
и доступной PostgreSQL. Для контейнера: `docker compose exec app alembic upgrade head`
(если сервис называется иначе, подставьте имя из compose). Затем пересоберите
сервисы командой `docker compose up --build -d`.

Панель специалиста находится в окне «Техподдержка» и доступна ролям `it`, `admin`.
Публичная регистрация разрешает только `kassir`; назначайте сотрудников через
администратора БД: `UPDATE users SET role='it' WHERE email='operator@example.com';`.
Пользователь видит свои заявки, сотрудник — общую очередь с фильтром и страницами. Статусы:
новая, в работе, решена. Для закрытия обязательно заполнить решение.
Права панели проверяются по актуальной роли в БД.

Подробная инструкция запуска, проверки и передачи: [HANDOFF.md](HANDOFF.md).

API `/api/v1/support`: GET /status; POST /sessions; GET /sessions/{id};
POST /sessions/{id}/messages с JSON message; GET /tickets;
GET /tickets/{id}; PATCH /tickets/{id} с JSON status, resolution, version, comment.
Общая очередь доступна с параметром queue=true только сотрудникам. Все методы требуют входа,
записывающие запросы также требуют разрешённый Origin из существующей конфигурации.
Диалоги доступны только создателю. Создание заявки и обновление истории атомарны;
блокировка строки и уникальный session_id предотвращают повторные заявки.

Проверки: `python -m unittest discover -s tests -p '*_unit.py'`
из backend; `npm install` и `npm run build` из frontend.
