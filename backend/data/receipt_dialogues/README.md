Шаг 3, версия 2026-11-09. Основание: [27 карточек покрытия](../RECEIPT_COVERAGE.md) и [24 процедуры](../RECEIPT_PROCEDURES.md). Это спецификация ожидаемого поведения, а не отчёт об успешной работе приложения.

Всего 1354 пользовательских ходов с допустимым следующим действием. Большая часть development — систематические вариации одних и тех же процедур, а не сотни разных неисправностей. Резервные случаи написаны отдельно; их тексты не дублируют development.

## Что покрыто

- Для каждой из 24 процедур и каждой из 27 карточек пробелов: полные/частичные данные, кнопки, свободный ввод с опечаткой, неизвестная модель, нечитаемая ошибка, исправление ответа, противоречие, помогло/не помогло/не смог выполнить.
- У всех 12 ready-процедур отдельно проверены все 85 обязательных условий: неизвестное значение и несовпадение. Проверены все шесть допустимых симптомов получения отчёта Пирит.
- Для каждой обязательной схемы/фотографии есть случай недоступности. Для каждой готовой процедуры — изменение отпечатка источника.
- Диагностические результаты рассмотрены отдельно: нулевой/ненулевой статус, пустой/не вышедший отчёт, связь без исправления исходной проблемы, включённый/выключенный/нечитаемый запрет печати, наличие/отсутствие/неизвестность бумаги.
- Общие переходы: согласие и отказ от заявки, ошибка сохранения, ошибка уведомления, устаревшая кнопка, неизвестный локальный IP, посторонний вопрос, бессмысленный ввод, запрет повторения без новых фактов.

Пробелы остаются теми же, что в аудите: наличие диалога не устраняет недостающую инструкцию. Для неготовой процедуры вариант «помогло» означает, что проблему устранил сам пользователь или внешний специалист; агент не должен приписывать себе исполнение заблокированных шагов.

## Как читать запись

Одна строка JSONL — один самостоятельный диалог. `target` связывает его с процедурой или карточкой пробела. `initial_context` — уже известные сведения этого обращения; пустой объект означает новый разговор. `environment` описывает контролируемые внешние условия, а не пользовательский текст.

У каждого хода есть `user` и `expect`:

- `allowed_next_actions` — допустимые альтернативы, достаточно одной; формулировки могут отличаться.
- `must_record` — факты, которые нужно сохранить; `null` означает неизвестно.
- `must_not` — запрещённые действия; любое нарушение проваливает ход.

`buttons` — семантические ответы, не жёстко заданные API ID. Адаптер должен нажать кнопку текущего вопроса с нужным смыслом. Если такой кнопки нет, это дефект нужного сценария, а не повод подставить ответ за пользователя.

Пример: после «Рулон установлен, но касса пишет “Нет бумаги”» сохраняются два факта: физически бумага есть, сообщение устройства — об её отсутствии. Разрешены применимая проверка или передача специалисту; запрещено записывать отсутствие рулона и ставить диагноз датчика без проверки.

Пример: после отчёта Пирит со статусом 0 и фразы «из программы всё ещё не печатает» допустимо предложить специалиста с результатом диагностики. Недопустимо завершить обращение как решённое.

## Правила оценки и будущего прогона

1. Начинать каждый диалог в отдельном обращении. Воспроизвести `initial_context` как подтверждённую историю; не делать предпосылки невидимыми для системы. Внешние условия задавать отдельно.
2. Передавать приложению только пользовательский ввод/историю. Не передавать ожидаемые действия, запреты, ID эталона, целевую процедуру или манифест в промпт.
3. Сравнивать смысл следующего действия и изменения фактов. При выдаче инструкции дополнительно проверить соответствие конкретной процедуре: порядок, ограничения, применимость, источник, обязательные изображения и проверка результата.
4. Если действие предыдущего хода не входит в допустимые — фиксировать дефект; не исправлять историю эталонным ответом для продолжения. Не требовать буквального совпадения фраз.
5. Непонятный для оценщика результат помечать «требует ручной проверки», а не автоматически считать успешным. `ask_relevant_fact` допускается только когда ответ действительно меняет выбор действия.
6. В итогах считать долю полностью пройденных диалогов, ошибки по шагам/процедурам/пробелам и отдельно критические нарушения: чужая модель, неготовая инструкция, выдуманный факт, потеря исправления, заявка без согласия.
7. Скорость измерять отдельно от семантической правильности: время каждого хода, p50/p95, холодный запуск отдельно. Числа скорости не измерялись при подготовке этих данных.

## Независимый итоговый набор

`holdout.jsonl` зарезервирован: не включать в подбор промптов, примеры RAG, fine-tuning или отладочные прогоны. Его ID и контрольная сумма зафиксированы в манифесте. До финального запуска закрепить версии кода, каталога и базы.

После знакомства с ошибками holdout он становится раскрытым набором. Повторный прогон после настройки допустим как регрессия, но для новой независимой оценки нужен новый резерв. Отдельный файл и контрольная сумма не являются техническим запретом на чтение — это правило процесса. Автор эталонов тот же; это отделение от настройки, не слепая внешняя экспертиза.

## Граница завершённого шага

Проверены структура записей, ссылки и полный набор требуемых вариантов; отсутствуют совпадающие диалоги между наборами. Сверены ограничения: заблокированные процедуры не выдаются как готовые, инструкция не заменяет диагностику, диагностика не равна решению. Приложение, Docker и физические кассы на этом шаге не запускались. Эталоны ещё предстоит подтвердить на реальном исполнителе; это не показатель его текущего качества.

Следующий этап: подключить каталог к исполнителю и сделать адаптер для этих семантических проверок. Сначала development; после исправлений и фиксации версии — один независимый прогон резерва.


## Шаг 4: сбор и обновление фактов

Реализация: `src/services/receipt_facts.py` извлекает наблюдения и применяет
исправления; `receipt_diagnosis.py` ведёт вопросы и результаты. Факты хранятся
в JSON состояния обращения, миграция БД не нужна. `receipt_facts` содержит
актуальные значения для заявки; внутри `_receipt` сохраняются конфликты и
ограниченная история изменений. Старые состояния переводятся в новый формат
при следующем сообщении.

- `None` — неизвестно; наличие бумаги и текст ошибки — разные поля.
- `error_status` различает отсутствие ошибки и невозможность прочитать её.
- Исправление модели отменяет зависимые настройки, источники и текущий план;
  явно сообщённые в этой же реплике новые сведения сохраняются.
- Короткое «нет» относится только к текущему вопросу. Конфликт уточняется;
  при невозможности уточнить предлагается специалист, без бесконечного опроса.
- Кнопки содержат номер вопроса; ответ от старого вопроса отклоняется существующей
  проверкой сервиса. Фронтенд уже передаёт полученный ID без преобразования.
- Доступ к сервисным действиям не извлекается из пользовательского заявления
  «я разрешаю». Доверенные права остаются задачей слоя авторизации.

Проверка: 800 development-сценариев прочитаны для проверки **слоя фактов**,
1912 явно заданных значений, плюс повторы известных вопросов при воспроизведении
реплик через обработчик. Проверены отдельные регрессии: отрицания, запасной рулон,
фразы об ошибке, предположения, исправления после предложения инструкции,
устаревшие кнопки и результат «не помогло» вместе с новым наблюдением.
Все 50 unit-тестов поддержки прошли. Это не утверждение о прохождении 800
полных сценариев поиска и выбора процедур: каталог ещё не подключён к исполнителю.
53 резервных диалога не использовались для настройки или прогона.

В development исправлены 17 некорректных ожиданий: строки «Неизвестная другая
модель» и «другая платформа» заменены на неизвестное значение, согласно исходному
контракту. Реплики и требование не выдавать неприменимую инструкцию сохранены;
изменения отмечены в `manifest.json`. Старый тест защиты от выдуманных LLM-фактов
переведён на обращение об ошибке приложения: вопрос о чеке теперь попадает в
детерминированную ветку и не проверял LLM вообще.

Повторить локальные проверки из `backend` в окружении с зависимостями проекта:

```powershell
python -m unittest discover -s tests -p "*unit.py"
```

Проверки используют подмены поиска и модели, не требуют Docker, GPU, БД или
скачивания весов. Локальный замер только сборщика фактов: медиана около 0,4 мс,
p95 около 1 мс; это не измерение полного времени ответа RAG.
