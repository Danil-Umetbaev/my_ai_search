# Передача программисту: агент диагностики

Это демонстрационная интеграция в существующий my_ai_search: FastAPI, React,
PostgreSQL/pgvector, локальная Qwen. Исходники, миграции и тесты входят в архив.
Дампы, пользовательские данные, модели, токены и `.env` в архив не входят.

## 1. Настройка

Из корня проекта скопируйте `.env.example` в `.env` (`Copy-Item .env.example .env`
для PowerShell; `cp .env.example .env` для bash). Задайте собственные
`POSTGRES_PASSWORD` и случайный `JWT_SECRET_KEY` длиной не меньше 32 символов.
Получить секрет: `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
Не меняйте пароль существующей PostgreSQL только через `.env`: уже созданная
база сохраняет прежние учётные данные.

`AUTH_TRUSTED_ORIGINS` должен содержать точный адрес, с которого открыт сайт,
включая порт. Для домена используйте HTTPS и `AUTH_COOKIE_SECURE=true`.
Для локального http оставьте false. `HF_TOKEN` опционален; достаточно прав Read.

## 2. Два режима демонстрации

### Полный ИИ-режим на сервере с NVIDIA

```bash
docker compose up -d --build
docker compose logs -f app
```

Откройте http://localhost:8080. Миграции применяются автоматически. Авторизация
и заявки работают, пока модели загружаются в фоне. `/api/v1/health` возвращает
`models: loading/ready/failed/disabled` и текущий `stage` загрузки. HTTP 200 health
означает готовность сайта, а `models=ready` — готовность ИИ и поиска.

Наполните базу знаний по README. Импорт также использует GPU; не запускайте его
параллельно с серверными моделями:

```bash
docker compose stop frontend app
docker compose run --rm --no-deps app python -m src.ai.ingestion.import_knowledge --limit 3
docker compose up -d
```

`--limit 3` — только проверка импорта; для полноценной базы уберите ограничение.
Наличие документа в базе само по себе не гарантирует подходящей инструкции
для выбранной неисправности. Данные исходного проекта не приложены.

### Быстрый режим без CUDA и скачивания моделей

```bash
docker compose -f docker-compose.yml -f docker-compose.support.yml up -d --build
```

Этот вариант собирает отдельный лёгкий образ, не требует NVIDIA и использует
резервную адаптивную диагностику. Подходит для показа полного процесса
«диалог → подтверждение → заявка → специалист → решение». Он явно подписан
в интерфейсе как резервный; это не демонстрация нейросетевого рассуждения.
Используйте актуальный Docker Compose с поддержкой YAML-тега `!reset`.

Оба варианта используют одно имя проекта и одну PostgreSQL. Не запускайте их
одновременно как независимые стенды. Для переключения на полный режим:
`docker compose up -d --build`. Не выполняйте `down -v`: удалятся данные.

## 3. Учётные записи и демонстрация заказчику

1. Зарегистрируйте пользователя в интерфейсе. Готовых паролей нет.
2. Зарегистрируйте вторую учётную запись сотрудника поддержки.
3. Назначьте сотруднику роль через CLI внутри сервера:

```bash
docker compose exec app python -m src.support_admin --email support@example.com --role it
```

Для лёгкого режима добавляйте `-f docker-compose.yml -f docker-compose.support.yml`
к командам Compose. После назначения сотрудник должен выйти и войти снова,
чтобы интерфейс увидел роль. API дополнительно проверяет актуальную роль в БД.
Публичная регистрация разрешает только `kassir`; роль `admin` также назначается CLI.

4. Войдите пользователем, откройте «Техподдержка» и напишите:
   «Сегодня на кассе 2 не печатается чек, перезапуск не помог».
5. Ответьте на уточнение о бумаге/индикаторах. Можно сразу выбрать
   «Нужен специалист». Просмотрите сводку, исправьте поле командой
   `окружение: касса 3`, затем нажмите «Подтвердить заявку».
6. В другом браузере войдите сотрудником. Откройте «Панель специалиста»,
   карточку заявки, измените статус на «В работе», сохраните комментарий.
7. Запишите решение, поставьте «Решена» и сохраните. Пользователь увидит
   решение и историю изменений в «Мои заявки» после обновления списка.

Номер заявки — UUID. В карточке видны собранные факты, неподтверждённые гипотезы,
источники, история ответов и полный диалог. Для завершения без заявки пользователь
пишет «проблема решена»; команда «отмена» также завершает диалог без заявки.

## 4. Устройство кода

| Файл | Ответственность |
| --- | --- |
| `backend/src/services/support_agent.py` | Структурированный план LLM, выбор вопроса/проверки, цитаты, fallback |
| `backend/src/services/diagnosis.py` | Адаптивные правила и переходы резервного сценария |
| `backend/src/services/support_dialogue.py` | Оркестрация диалога, подтверждение, идемпотентность, права, заявки |
| `backend/src/repositories/support.py` | Запросы к PostgreSQL |
| `backend/src/models/support.py` | ORM-метаданные таблиц поддержки |
| `backend/src/schemas/support.py` | Схемы запросов и ответов API |
| `backend/src/api/v1/support.py` | HTTP-маршруты поддержки |
| `backend/src/middleware/ai_capacity.py` | Общая очередь GPU, лимиты, дедлайн поддержки |
| `frontend/src/components/SupportWorkspace.jsx` | Диалог, мои заявки, рабочее место специалиста |
| `backend/src/support_admin.py` | Назначение ролей без публичной выдачи привилегий |

LLM имеет только два доступных приложению действия с внешними данными:
поиск документации и выдача структурированного плана. Команды ОС, доступ к кассам,
отправка платежей и произвольные инструменты ей не предоставлены. Факты принимаются
как выдержки из сообщений пользователя. Исправления сохраняют прежнее значение.
Приложение проверяет JSON, допустимые действия, ссылки и дословность цитат.
Проверки с очевидными опасными командами отклоняются. Это не семантическое
доказательство безопасности или применимости любой цитаты: инструкции проверяют
на своей базе знаний и версиях ПО.

Состояния: `collect/check` (правила), `diagnosing` (LLM), `verify_resolution`,
`confirm`, `ticket_created`, `resolved`, `cancelled`. Заявку создаёт только
приложение после отдельного подтверждения в `confirm`; LLM не пишет в БД напрямую.
В `resolved/cancelled` дальнейшие сообщения не создают заявку.

Дедлайн `SUPPORT_MODEL_TIMEOUT_SECONDS` ограничивает ожидание модели, по умолчанию
45 секунд. GPU-задача после дедлайна может закончить вычисление в фоне; она
не меняет диалог и продолжает удерживать общий GPU-lock. В очереди не больше
16 задач поддержки, чтобы таймауты не порождали неограниченные фоновые вычисления.
Генерация плана дополнительно ограничена числом токенов и мягким `max_time`.

Медленный вызов LLM не удерживает блокировку строки диалога. После получения
ответа сервис коротко блокирует строку, проверяет версию и атомарно сохраняет
историю и заявку. Конкурирующие изменения дают 409. Повтор запроса с тем же
`request_id` возвращает прежний ответ без повторной записи. Изменение содержимого
при том же идентификаторе запрещено. Клиент сохраняет request_id при сетевой ошибке.
Уникальный session_id в заявках дополнительно исключает вторую заявку из диалога.

## 5. API

Все маршруты находятся под `/api/v1/support`, требуют cookie авторизации;
изменяющие запросы также проверяют Origin.

| Метод и путь | Назначение |
| --- | --- |
| `GET /status` | Режим агента и наличие базы знаний |
| `POST /sessions` | Новый диалог |
| `GET /sessions/{id}` | Состояние, история и версия своего диалога |
| `POST /sessions/{id}/messages` | `{ "message": "...", "request_id": "UUID" }` |
| `GET /tickets` | Свои заявки; `status`, `offset`, `limit` |
| `GET /tickets?queue=true` | Общая очередь для it/admin |
| `GET /tickets/{id}` | Карточка, диалог и журнал событий; владелец или it/admin |
| `PATCH /tickets/{id}` | it/admin: `status`, `version`, `resolution`, `comment`, `assign_to_me` |

Сообщение: до 4000 символов. Ответ: `answer`, `ticket_id`, `request_id`, `version`,
`phase`, `engine`. Поддерживаемые статусы заявки: `open/in_progress/resolved`.
Для resolved обязательно решение. Комментарии видны автору, внутренних заметок нет.
Перед PATCH берите `version` из свежей карточки; при 409 перечитайте её.
Чужие диалоги и заявки возвращают 404, общая очередь без роли — 403.
Лимит диалога — 60 пар сообщений; для дальнейшей работы создайте новый.

## 6. Проверки без моделей

Все API-тесты используют отдельную базу `<DB_NAME>_tests`. Команда очистки тестов
затрагивает только её. Создайте её один раз (обычные параметры примера ниже):

```bash
docker compose exec db createdb -U search my_ai_search_tests
docker compose run --rm --no-deps -e DB_NAME=my_ai_search_tests app alembic upgrade head
docker compose run --rm --no-deps -e LOAD_SEARCH_MODELS=false -v ./backend:/backend app python -m pytest tests/test_diagnosis_unit.py tests/test_support_agent_unit.py tests/integration/test_support.py tests/integration/test_health.py -q
```

Тесты не включены в рабочий образ, поэтому последняя команда монтирует исходники.
Если изменили POSTGRES_DB/POSTGRES_USER, замените имена в командах соответственно.
Для лёгкого образа используйте те же команды с дополнительным Compose-файлом.
Проверка фронтенда: `cd frontend`, `npm ci`, `npm run build` (Node.js 22).

API-тесты покрывают авторизацию и Origin, изоляцию пользователей, резервный и
модельный пути с подменённым планировщиком, подтверждение, повторные запросы,
конкурентную отправку, статусы, решение, версии и историю событий.
Unit-тесты проверяют JSON, недостоверные факты и цитаты, отсутствие модели,
таймауты, сбои поиска, исправления и завершение диалога.

Реальная Qwen и качество поиска не подменяются обещанием прохождения unit-тестов:
перед демонстрацией ИИ-качества на сервере проведите несколько диалогов на своей
документации. Репозиторий содержит старые тесты поиска с прежними ожиданиями
статуса `escalated`; они не определяют контракт нового агента поддержки.

## 7. Обновление и границы примера

Новые миграции: `support_agent_01` (таблицы) и `support_workflow_02` (версии,
индексы, журнал событий). Существующая история сохраняется. На обновляемом
сервере сделайте резервную копию БД; не удаляйте volumes. Свою `.env` храните отдельно.

Эта поставка — пример для демонстрации и дальнейшей разработки, а не обещание
поддержки произвольного оборудования. Нет удалённого выполнения команд, SLA,
почтовых уведомлений по заявкам, вложений или интеграции с внешним helpdesk.
Старый публичный поиск проекта остаётся отдельным модулем; анонимные поисковые
диалоги не получают разграничения доступа от новых таблиц поддержки.
